## 1. مقدمة

### 1.1 الغرض

تحدد هذه الوثيقة المتطلبات الوظيفية وغير الوظيفية لنظام إدارة وتشغيل مطعم فتوش. وهي المرجع الأساسي للمراحل التالية: تصميم المعمارية، تصميم البيانات، تصميم الواجهات، خطة التنفيذ، الاختبارات والتشغيل.

### 1.2 أهداف النظام

1. إنشاء نظام جديد مستقل لإدارة المطعم وطلباته وعملائه والكاشير والمطبخ والطباعة.
2. توفير تجربة طلب سهلة للعميل من خلال موقع متجاوب وتطبيق ويب تقدمي (PWA).
3. توفير لوحة إدارة شاملة لإعداد المطعم والمنتجات والطلبات والمستخدمين والتقارير.
4. توفير شاشة كاشير عملية لإدارة الطلبات والمدفوعات والوردية والطباعة.
5. دعم الطباعة الآلية واليدوية مع إمكانية معرفة حالة كل مهمة طباعة وإعادة المحاولة دون تكرار الطلب.
6. بناء بنية قابلة للتوسع لدعم فروع إضافية مستقبلًا.
7. حماية البيانات وسلامة العمليات المالية والطلبات، مع سجل واضح للعمليات المهمة.
8. تصميم النظام لتحمل زيادة الزيارات والطلبات المتزامنة، ثم قياس السعة الفعلية باختبارات أداء قبل اعتماد أي أرقام تشغيلية.

### 1.3 خلفية المشروع وحدوده

النظام مخصص لمطعم **فتوش الخالدية** في الكويت. يبدأ التشغيل المستهدف بفرع واحد، مع تصميم يسمح بالتوسع إلى عدة فروع لاحقًا. هذا المشروع جديد ومنفصل تمامًا عن الأنظمة والمستودعات وقواعد البيانات السابقة.

### 1.4 المصطلحات

| المصطلح | التعريف |
|---|---|
| PWA | تطبيق ويب تقدمي قابل للتثبيت على الأجهزة المتوافقة |
| Modular Monolith | تطبيق واحد مقسم إلى وحدات وظيفية ذات حدود وعقود واضحة |
| Module Manager | إدارة تفعيل وتعطيل الوحدات بعد فحص الاعتماديات |
| Print Agent | برنامج/خدمة وسيطة تتعامل مع الطابعة المحلية وتنفذ مهام الطباعة |
| KWD | الدينار الكويتي |
| بيئة التطوير | بيئة منفصلة للتجارب والاختبارات |
| بيئة الإنتاج | البيئة الرسمية المستخدمة في المطعم |
| الحد الأدنى للطلب | أقل قيمة مسموح بها لطلب التوصيل في منطقة معينة |
| مهمة الطباعة | سجل مستقل لطلب إرسال مستند إلى طابعة محددة |

## 2. نطاق النظام

### 2.1 داخل النطاق

- واجهة العميل لعرض القائمة والمنتجات والخيارات والسلة وإنشاء الطلب ومتابعته.
- حسابات العملاء والطلبات السابقة والعناوين والمفضلة والتقييمات والدعم.
- لوحة الإدارة لإدارة بيانات المطعم ومحتواه ومنتجاته وطلباته ومستخدميه وإعداداته.
- شاشة الكاشير لإدارة الطلبات والبيع اليدوي والمدفوعات والوردية والطباعة.
- إعداد مناطق التوصيل ورسومها وحدود الطلب الدنيا.
- إدارة المطبخ والطابعات ومهام الطباعة وسجلاتها.
- تقارير تشغيلية ومالية وسجلات تدقيق.
- إدارة النسخ الاحتياطي والاستعادة ومراقبة النظام والأخطاء.
- تصميم يسمح بإدارة الفروع مستقبلًا.

### 2.2 خارج النطاق حاليًا

- تعديل أو ترحيل أو حذف أو إعادة استخدام ملفات أو قواعد بيانات أو إعدادات النظام القديم.
- اعتماد مزود دفع إلكتروني أو شركة رسائل أو مزود خرائط بعينه قبل قرار منفصل.
- ضمان عدد محدد من الطلبات في الثانية أو المستخدمين المتزامنين دون اختبار وقياس.
- إطلاق عدة فروع فعليًا في النسخة الأولى.
- التحول إلى Microservices دون مبرر تقني وتشغيلي موثق.

## 3. المستخدمون والصلاحيات

### 3.1 أنواع المستخدمين الرئيسية

يوجد ثلاثة أنواع رئيسية فقط:

1. **العميل:** يتصفح القائمة ويُنشئ طلبًا ويتابع طلباته ويدير بياناته.
2. **الكاشير:** يستقبل الطلبات ويدير الطلبات والمدفوعات والوردية والمطبخ والطباعة ضمن صلاحياته.
3. **المدير (Admin):** يدير النظام وإعداداته ومستخدميه وتقاريره ووحداته.

يمكن إنشاء أدوار إدارية داخل نوع المدير، ومنح صلاحيات تفصيلية لكل دور. لا يُنشأ نوع مستخدم رئيسي رابع.

### 3.2 متطلبات الصلاحيات

- يجب أن تكون الصلاحيات مبنية على الأدوار مع إمكانية منح أو منع صلاحيات محددة.
- يجب تطبيق مبدأ أقل صلاحية لازمة.
- يجب حماية الصفحات والعمليات والواجهات الخلفية، لا إخفاء الأزرار فقط.
- يجب تسجيل العمليات الحساسة مثل تعديل الأسعار والرسوم والصلاحيات والإعدادات المالية.
- يجب إبطال الجلسات أو صلاحيات الوصول عند تعطيل الحساب أو تغيير بيانات الأمان حسب السياسة المعتمدة.
- لا يجوز للكاشير الوصول إلى وظائف الإدارة العليا إلا إذا مُنح صلاحية صريحة ومحددة.

## 4. قواعد العمل الأساسية

### 4.1 أنواع الطلب

- الأنواع المتاحة: **استلام من المطعم** و**توصيل** فقط.
- لا يوجد خيار «استلام من السيارة».
- يجب أن يؤثر اختيار النوع على الحقول المطلوبة والرسوم والحد الأدنى المعروض.

### 4.2 الاستلام من المطعم

- الاسم ورقم الهاتف مطلوبان.
- لا يُطلب عنوان للاستلام.
- لا يطبق حد أدنى للطلب على الاستلام.
- لا تُضاف رسوم توصيل إلى طلب الاستلام.
- يجب إظهار طريقة الاستلام وتعليمات/وقت التجهيز وفق الإعدادات المتاحة.

### 4.3 التوصيل

- يجب تحديد منطقة التوصيل والعنوان قبل تأكيد الطلب.
- يطبق الحد الأدنى ورسوم التوصيل المحددان للمنطقة المختارة.
- يجب عرض الحد الأدنى ورسوم التوصيل بوضوح قبل تأكيد الطلب.
- إذا لم يحدد العميل المنطقة ثم حاول إضافة أول صنف إلى السلة، يجب مطالبته بتحديد المنطقة أو إظهار متطلبات التوصيل قبل الاستمرار في مسار التوصيل. لا ينبغي فرض اختيار منطقة على من يطلب الاستلام.
- يجب إعادة التحقق من تغطية المنطقة والحد الأدنى والرسوم عند إتمام الطلب، وليس الاعتماد على قيمة قديمة محفوظة في واجهة العميل.

### 4.4 حقول العنوان

الحقول المعتمدة:

1. المحافظة.
2. المنطقة.
3. القطعة.
4. الشارع.
5. الجادة — اختياري.
6. رقم المنزل.
7. الدور — اختياري.
8. الشقة — اختياري.

يجب تحديد الحقول الإلزامية والاختيارية كما هو موضح. ويمكن إضافة ملاحظات العنوان أو علامة مميزة عند اعتمادها في تصميم الواجهة.

### 4.5 المنتجات والسندويتشات

- لكل منتج اسم ووصف وسعر وحالة توفر وصورة أو صور حسب سياسة الصور المعتمدة.
- جميع السندويتشات تستخدم خبز الصمون افتراضيًا، إلا إذا كان اسم/وصف الصنف يحدد صراحة نوع خبز آخر مثل خبز الصاج.
- خيارات الإضافات والحذف والاستبدال يجب أن تنعكس في تفاصيل الطلب والسعر النهائي.
- مكونات أصناف صواني المشويات تظهر داخل تفاصيل الصنف فقط، ولا تظهر في قائمة المنتجات الرئيسية.

### 4.6 التسعير والحساب

- الأسعار بالدينار الكويتي.
- يجب أن تكون حسابات الإجمالي والخصم والرسوم على الخادم هي المرجع النهائي.
- يجب إعادة التحقق من السعر والتوفر والخيارات عند الإضافة للسلة وعند تأكيد الطلب.
- يجب توضيح قيمة الأصناف والخصم ورسوم التوصيل والإجمالي النهائي كلٌ على حدة.
- لا يسمح بتكرار تطبيق الخصم أو رسوم التوصيل بسبب إعادة إرسال الطلب.

### 4.7 دورة حياة الطلب

تجربة العميل مبسطة: بعد إرسال الطلب يظهر تأكيد الطلب والفاتورة، ولا تُعرض للعميل مراحل متابعة تشغيلية مثل «قيد التجهيز» أو «تم التجهيز» أو «جاهز للاستلام» أو «في الطريق».

- يحتفظ النظام بسجل داخلي للطلب لأغراض التشغيل والتدقيق والطباعة والإلغاء، دون عرض مراحل متابعة للعميل.
- يُسمح للعميل بإلغاء الطلب في أي وقت قبل استلامه، حتى لو بدأ المطعم التجهيز.
- عند الإلغاء، تصدر/تُطبع فاتورة تحتوي على تفاصيل الطلب وتظهر كلمة «ملغي» بوضوح في أعلى الفاتورة.
- يجب تسجيل من نفذ الإلغاء ووقته، مع الحفاظ على سجل الطلب والفاتورة.

### 4.8 الدفع

وسائل الدفع المتاحة ضمن نطاق الإطلاق الأول:
- الدفع النقدي.
- الدفع باستخدام جهاز كي نت، سواء عند الاستلام من المطعم أو عند التوصيل.
- الدفع عبر رابط دفع؛ يوضح الطلب/الفاتورة أن وسيلة الدفع هي «رابط دفع»، ويتولى الكاشير إرسال الرابط إلى العميل.

وسائل تُجهز معماريًا وتقنيًا دون تفعيلها في الإطلاق الأول:
- الدفع بالبطاقات عبر الإنترنت.
- Apple Pay.
- المحافظ الإلكترونية.

متطلبات عامة:
- يجب تسجيل وسيلة الدفع وحالتها بصورة مستقلة عن حالة الطلب.
- يجب منع تسجيل العملية المالية مرتين عند تكرار الإرسال أو إعادة المحاولة.
- يجب ألا يُسجل الدفع عبر رابط على أنه ناجح إلا بعد تأكيد موثوق من مزود الدفع.
- عند اختيار العميل الدفع عبر الرابط، تظهر وسيلة الدفع في الفاتورة بوضوح بصيغة «طريقة الدفع: رابط دفع»، ويتولى الكاشير إرسال رابط الدفع إلى العميل.
- لا ينشئ النظام الرابط أو يرسله تلقائيًا ضمن التدفق المعتمد حاليًا؛ طريقة إنشاء/استخراج الرابط ومزوده ما زالت تحتاج تحديدًا قبل التكامل.
- يجب أن يستطيع الكاشير معرفة أن رابط الدفع مطلوب وإتمام خطوة إرساله، مع تسجيل حالة الدفع بصورة مستقلة؛ ولا يُعد إرسال الرابط دليلًا على نجاح الدفع.
- يجب تحديد مزود رابط الدفع وآلية تكامل جهاز كي نت أو تسجيل عملياته قبل تنفيذ تكامل الدفع.
- يجب تحديد قواعد التسوية والاسترداد والإلغاء المالي قبل تشغيل مسارات الدفع الإلكتروني.

### 4.9 الطباعة

- الطابعة المستهدفة: Epson TM-T20.
- مطلوب دعم Print Agent مستقل، مع استهداف الطباعة من أجهزة Android عبر USB.
- إنشاء الطلب بنجاح لا يعني نجاح الطباعة؛ لكل منهما حالة مستقلة.
- يجب تسجيل مهمة الطباعة وحالتها ومحاولاتها ووقت التنفيذ ورسالة الخطأ إن وجدت.
- يجب توفير إعادة طباعة بصلاحية مناسبة مع تسجيل من طلبها وسببها عند اعتماد السياسة.
- يجب منع التكرار غير المقصود، مع السماح بإعادة طباعة صريحة.
- يجب أن تكون الفاتورة/تذكرة المطبخ واضحة ومنظمة وتعرض الأصناف وخياراتها والكميات وملاحظات الطلب ونوعه وبياناته الضرورية.

## 8. المتطلبات التفصيلية للطلبات

### 8.1 إنشاء طلب العميل

1. يعرض النظام الأقسام والمنتجات المتاحة.
2. يختار العميل الصنف والخيارات المطلوبة.
3. يحدد نوع الطلب: استلام أو توصيل.
4. في حالة الاستلام، يُطلب الاسم ورقم الهاتف فقط كبيانات أساسية.
5. في حالة التوصيل، يُطلب تحديد المنطقة والعنوان، ويُحسب الحد الأدنى ورسوم المنطقة.
6. يعرض النظام ملخصًا كاملًا قبل التأكيد.
7. يتحقق الخادم من الأسعار والتوفر والخيارات والحد الأدنى والرسوم.
8. ينشئ النظام الطلب برقم فريد وحالة ابتدائية واضحة.
9. يعرض تأكيدًا للعميل ويبدأ مسار التحديث والطباعة وفق الإعدادات.

### 8.2 السلة والتزامن

- يجب ألا يؤدي النقر المكرر أو إعادة إرسال الطلب إلى إنشاء طلبات مكررة.
- يجب التعامل مع تغير سعر المنتج أو نفاد الكمية بين فتح القائمة وتأكيد الطلب.
- يجب إعادة حساب الإجمالي على الخادم.
- يجب حماية تحديثات السلة والطلب من التعارضات عند وصول طلبات متزامنة.
- يجب تحديد مدة صلاحية السلة وسياسة الاحتفاظ بها في مرحلة التصميم.

### 8.3 تعديل الطلب

- يجب تحديد الحالات التي تسمح بالتعديل.
- أي تعديل بعد بدء التحضير يتطلب سياسة وصلاحية محددة.
- يجب تسجيل القيمة السابقة والجديدة والسبب والمستخدم.
- يجب إعادة حساب الإجمالي وأثر الدفع عند أي تعديل مالي.

## 9. متطلبات المطبخ والطباعة

### 9.1 بنية الطباعة

تكون الطباعة من خلال مكوّن Print Agent مستقل عن منطق إنشاء الطلب. يتلقى الوكيل مهامًا محددة، ويرسلها إلى الطابعة المتصلة بالجهاز، ثم يعيد حالة التنفيذ.

### 9.2 حالات مهمة الطباعة

يجب تصميم حالات واضحة مثل: في الانتظار، قيد الإرسال، تمت الطباعة، فشلت، تحتاج إعادة محاولة، أُلغيت. القائمة النهائية تُعتمد في تصميم الطباعة.

### 9.3 متطلبات الاعتمادية

- لا يتوقف حفظ الطلب بسبب تعطل الطابعة.
- فشل الطباعة لا يغير حالة الطلب إلى فشل.
- يجب الاحتفاظ بسجل مهمة الطباعة ومحاولاتها وسبب الفشل.
- يجب توفير إعادة المحاولة وفق سياسة تمنع التكرار غير المقصود.
- يجب التمييز بين النسخة الأصلية وإعادة الطباعة.
- يجب إظهار حالة Print Agent والطابعة في شاشة الكاشير/الإدارة حسب الصلاحية.
- يجب اختبار Epson TM-T20 عمليًا على بيئة Android وUSB المستهدفة قبل اعتماد التوافق النهائي.
- يجب توثيق الأجهزة وأنظمة Android والتوصيلات المدعومة بعد الاختبار.

### 9.4 محتوى تذكرة المطبخ

تحتوي التذكرة، حسب نوعها، على رقم الطلب ووقت الإنشاء ونوع الطلب والأصناف والكميات والخيارات والإضافات والمحذوفات وملاحظات العميل والبيانات اللازمة للتحضير. لا تعرض معلومات شخصية غير ضرورية للمطبخ.

## 10. المتطلبات غير الوظيفية

### 10.1 الأداء وقابلية التوسع

- يجب تصميم الصفحات والواجهات لتقليل الاستعلامات غير الضرورية.
- استخدام Redis للتخزين المؤقت والصفوف الخلفية حيث يكون ذلك مناسبًا.
- استخدام فهارس قاعدة البيانات للاستعلامات المتكررة.
- تنفيذ الأعمال الثقيلة وغير الفورية عبر Queue/Workers.
- استخدام Pagination وعمليات بحث محددة بدل تحميل بيانات غير محدودة.
- تطبيق Rate Limiting على نقاط الدخول الحساسة.
- حماية عمليات إنشاء الطلب والدفع وتحديث المخزون من التزامن والتكرار.
- مراقبة زمن الاستجابة ومعدل الأخطاء واستهلاك الموارد.
- تنفيذ اختبارات حمل واختبارات ضغط قبل الإطلاق وتوثيق نتائجها.
- لا تُعتمد أرقام أداء أو سعة قصوى إلا بعد الاختبار على بنية مماثلة للإنتاج.

### 10.2 الأمان والخصوصية

- تشفير الاتصال باستخدام HTTPS في الإنتاج.
- تخزين كلمات المرور باستخدام آليات تجزئة آمنة يوفرها إطار العمل.
- حماية الجلسات والكوكيز وواجهات الطلب من الهجمات الشائعة.
- التحقق من الصلاحيات على الخادم لكل عملية حساسة.
- حماية الأسرار ومفاتيح التكامل وعدم حفظها في المستودع.
- تقليل جمع البيانات الشخصية إلى الحد اللازم للتشغيل.
- عدم تسجيل كلمات المرور أو رموز الدفع أو الأسرار في السجلات.
- وضع سياسة احتفاظ وحذف للبيانات بعد اعتماد المتطلبات القانونية والتشغيلية.

### 10.3 الاعتمادية والتوافر

- يجب التعامل مع فشل Redis أو الطابعة أو خدمات التكامل بصورة لا تؤدي إلى فقد الطلبات.
- يجب أن تكون العمليات الحرجة قابلة للتعافي وإعادة المحاولة الآمنة.
- يجب توفير نسخ احتياطي دوري واختبار الاستعادة.
- يجب فصل الأعطال الجزئية؛ فتعطل الطباعة لا يمنع تسجيل الطلب.
- يجب توثيق إجراءات استعادة الخدمة بعد الأعطال.

### 10.4 سهولة الاستخدام وإمكانية الوصول

- واجهات عربية واضحة ومتجاوبة مع الهاتف والكمبيوتر.
- تقليل خطوات إنشاء الطلب والكاشير قدر الإمكان.
- تمييز الحالات والأخطاء والتنبيهات بصريًا ونصيًا.
- عدم الاعتماد على اللون وحده لشرح الحالة.
- توفير رسائل خطأ مفهومة وإرشادات قابلة للتنفيذ.

### 10.5 الصيانة وقابلية الاختبار

- كتابة اختبارات آلية للوحدات والتكامل والعمليات الحرجة.
- استخدام migrations لإدارة تغييرات قاعدة البيانات.
- توثيق عقود الوحدات والأحداث والخدمات.
- توحيد معالجة الأخطاء والسجلات.
- اعتماد مراجعة التغييرات قبل دمجها في الفرع الرئيسي.
- عدم إجراء تغييرات إنتاجية مباشرة دون خطة نشر وتراجع.

| قاعدة البيانات | MySQL 8 |
| واجهة المستخدم | Laravel Livewire + Alpine.js |
| Cache & Queue | Redis |
| تطبيق العميل | PWA |
| الطباعة | Print Agent مستقل |

### 11.2 Modular Monolith

- تطبيق واحد مقسم إلى وحدات وظيفية منظمة.
- لكل وحدة مسؤولية وحدود واضحة.
- التواصل بين الوحدات عبر خدمات/واجهات/أحداث موثقة.
- منع الاعتماد الدائري والوصول العشوائي إلى التفاصيل الداخلية.
- Module Manager لا يسمح بتعطيل وحدة تعتمد عليها وحدات أخرى دون معالجة الاعتمادية.
- لا يتم حذف ملفات الوحدة لتعطيلها؛ يتم ذلك عبر آلية إدارية آمنة وفحوصات مسبقة.
- لا يُتخذ قرار التحول إلى Microservices إلا بعد قياس الحاجة وتوثيق التكلفة والفائدة.

### 11.3 فصل البيئات

- بيئة تطوير مستقلة.
- بيئة اختبار/تجهيز قبل الإنتاج عند اعتماد خطة النشر.
- بيئة إنتاج مستقلة.
- قاعدة بيانات الإنتاج منفصلة تمامًا عن قاعدة التطوير.
- عدم استخدام بيانات الإنتاج في التطوير إلا بعد إخفاء/تجريد البيانات الحساسة وموافقة صريحة.
- إعدادات وأسرار كل بيئة منفصلة.

### 11.4 تعدد الفروع

يبدأ النظام بفرع فتوش الخالدية. يجب ألا تمنع بنية البيانات والتصميم إضافة فروع لاحقًا. يجب تحديد نطاق البيانات والصلاحيات والمنتجات والأسعار والمناطق والطابعات حسب الفرع في مرحلة تصميم قاعدة البيانات.

## 12. البيانات والتكاملات

### 12.1 مجموعات البيانات الرئيسية المتوقعة

- المستخدمون والأدوار والصلاحيات والجلسات.
- العملاء وملفاتهم وعناوينهم وتفضيلاتهم.
- الفروع وإعداداتها.
- الأقسام والمنتجات والصور والخيارات.
- الأسعار والعروض والقسائم.
- مناطق التوصيل والرسوم والحد الأدنى.
- الطلبات وبنود الطلب وتاريخ الحالات.
- المدفوعات والاستردادات وحركات الصندوق.
- مهام الطباعة والطابعات والأجهزة.
- الورديات وسجلات الكاشير.
- الإشعارات والتقييمات والدعم.
- السجلات والتدقيق والنسخ الاحتياطية وإعدادات النظام.

هذه قائمة مفاهيمية وليست تصميم جداول نهائيًا.

### 12.2 التكاملات المحتملة

قد يحتاج النظام إلى بوابة دفع ورسائل نصية/إشعارات وخدمات خرائط أو تكاملات أخرى. لا يتم اختيار أي مزود قبل تقييم التكلفة والتوافق والمتطلبات التشغيلية والأمنية واعتماد القرار.

## 13. السجلات والتدقيق

يجب تسجيل الأحداث المهمة، ومنها:
- تسجيل الدخول والخروج ومحاولات الدخول الفاشلة.
- إنشاء الطلب وتعديله وإلغاؤه وتغيير حالته.
- تغيير السعر أو رسوم التوصيل أو الحد الأدنى أو الخصم.
- تسجيل الدفع والاسترداد.
- بدء الوردية وإغلاقها وحركات الصندوق.
- إنشاء المستخدمين وتعديل الأدوار والصلاحيات.
- تفعيل/تعطيل وحدة أو تغيير إعداد نظام.
- إنشاء نسخة احتياطية أو استعادة بيانات.
- إنشاء مهمة طباعة أو فشلها أو إعادة طباعتها.

يجب أن تحتوي السجلات على الحد الأدنى اللازم للتحقيق، وألا تتضمن أسرارًا أو بيانات دفع حساسة.

## 14. النسخ الاحتياطي والاستعادة

- وضع سياسة نسخ احتياطي لقاعدة البيانات والملفات المهمة.
- تحديد دورية النسخ ومدة الاحتفاظ ومكان التخزين الآمن.
- تقييد صلاحية الاستعادة على أدوار محددة جدًا.
- تسجيل كل عملية نسخ واستعادة ونتيجتها.
- إجراء اختبار استعادة دوري، لأن وجود نسخة احتياطية دون اختبار لا يثبت إمكانية الاستعادة.
- اعتماد أهداف RPO وRTO بعد تحديد الاستضافة والميزانية ومتطلبات التشغيل.

## 15. متطلبات الاختبار ومعايير القبول العامة

لا تعتبر المرحلة مكتملة لمجرد ظهور الواجهة. يجب اختبار السلوك والبيانات والصلاحيات وحالات الفشل.

### 15.1 سيناريوهات قبول حرجة

1. يستطيع العميل إنشاء طلب استلام بالاسم والهاتف دون عنوان ودون حد أدنى أو رسوم توصيل.
2. لا يستطيع العميل تأكيد طلب توصيل قبل استكمال المنطقة والعنوان الإلزامي.
3. يظهر الحد الأدنى ورسوم التوصيل الصحيحة للمنطقة المختارة.
4. يمنع النظام تأكيد طلب توصيل أقل من الحد الأدنى المطبق.
5. تظهر حقول الجادة والدور والشقة كاختيارية.
6. لا تظهر مكونات صواني المشويات في قائمة المنتجات الرئيسية، وتظهر داخل تفاصيل الصنف.
7. يستخدم السندويتش الصمون افتراضيًا إلا إذا حُدد نوع خبز مختلف للصنف.
8. لا يؤدي إرسال طلب مرتين أو النقر المتكرر إلى إنشاء طلبين متطابقين.
9. يسجل تغيير حالة الطلب مع المستخدم والتوقيت.
10. لا يؤدي فشل الطابعة إلى فقد الطلب أو اعتباره فاشلًا.
11. يمكن تتبع مهمة الطباعة ومعرفة سبب فشلها وإعادة طباعتها بصلاحية.
12. يمنع النظام المستخدم من تنفيذ وظيفة لا تسمح بها صلاحياته حتى لو حاول الوصول المباشر.
13. يمكن استعادة نسخة احتياطية في بيئة اختبار وفق الإجراء الموثق.
14. تعمل واجهة العميل على أحجام شاشات الهاتف والكمبيوتر الأساسية.
15. تنجح اختبارات الحمل المتفق عليها قبل الإطلاق وفق أهداف أداء تعتمد لاحقًا.

### 15.2 أنواع الاختبار

- Security Tests.

- Backup & Restore Tests.
