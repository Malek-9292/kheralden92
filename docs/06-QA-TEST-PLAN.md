## 1. الهدف والنطاق

تحدد هذه الوثيقة أسلوب التحقق من أن نظام فتوش الجديد يطابق المتطلبات المعتمدة، ويحافظ على سلامة الطلبات والحسابات والصلاحيات، ويعمل بصورة مستقرة في ظروف التشغيل الطبيعية وحالات الفشل.

الأهداف:

1. تحويل متطلبات SRS ومعايير القبول إلى حالات اختبار قابلة للتنفيذ.
2. اكتشاف العيوب مبكرًا قبل دمج الكود أو نشره.
3. التحقق من قواعد الاستلام والتوصيل والتسعير والطلبات.
4. التحقق من الصلاحيات وحماية البيانات والعمليات الحساسة.
5. اختبار التزامن ومنع التكرار في الطلبات والمدفوعات والطباعة.
6. اختبار التكامل بين Laravel وMySQL وRedis والصفوف وPrint Agent.
7. اختبار واجهات العميل والكاشير والإدارة على الأجهزة المستهدفة.
8. إثبات النسخ الاحتياطي والاستعادة عمليًا.
9. قياس الأداء على بيئة مماثلة للإنتاج دون ادعاء سعة غير مقاسة.
10. تحديد بوابات قبول تمنع الانتقال للإطلاق مع وجود عيوب حرجة.

## 2. مبادئ الاختبار

- المتطلبات المعتمدة هي المرجع؛ لا يغير الاختبار قاعدة عمل دون قرار موثق.
- كل وظيفة حرجة يجب أن ترتبط بواحدة أو أكثر من حالات الاختبار.
- يجب اختبار السلوك على الخادم، وليس شكل الواجهة فقط.
- الاختبارات تستخدم بيئات وبيانات مستقلة عن الإنتاج.
- لا تستخدم بيانات العملاء الحقيقية في بيئة الاختبار إلا وفق سياسة معتمدة لإخفاء الهوية والموافقة.
- حالات النجاح والفشل والانقطاع والتكرار والتعارض يجب أن تكون ممثلة.
- فشل الطباعة لا يعني فشل إنشاء الطلب.
- حالة الطلب وحالة الطباعة مستقلة ويجب اختبارهما منفصلتين؛ لا توجد حالة دفع ضمن النطاق الحالي.
- الاختبارات الآلية لا تلغي اختبار الاستخدام على أجهزة حقيقية.
- لا تُقبل نتيجة اختبار غير موثقة بالبيئة والإصدار والبيانات والخطوات.
- لا تُعلن أي نتيجة نجاح قبل تنفيذ الاختبار وتسجيل الدليل.

## 3. مستويات وأنواع الاختبار

| النوع | الهدف | نطاق أمثلة |
|---|---|---|
| Unit Tests | اختبار منطق صغير بمعزل عن الخدمات الخارجية | حساب الإجمالي، قواعد الحد الأدنى، انتقالات الحالة |
| Feature Tests | اختبار وظيفة من خلال Laravel | تسجيل الدخول، إنشاء الطلب، تعديل المنتج |
| Integration Tests | اختبار تفاعل أكثر من مكوّن | Laravel مع MySQL وRedis وQueue |
| API / Contract Tests | التحقق من العقود والبيانات بين المكونات | Print Job API وعقود الأحداث |
| End-to-End (E2E) | اختبار تدفق مستخدم كامل | عميل يطلب، كاشير يتابع، مطبخ يطبع |
| Authorization Tests | التحقق من الأدوار والصلاحيات | منع كاشير من تغيير صلاحية مدير |
| Security Tests | التحقق من الثغرات وسوء الاستخدام | جلسات، مدخلات، رفع ملفات، أسرار |
| Concurrency / Idempotency | التحقق من التزامن ومنع التكرار | إرسال الطلب مرتين وتحديث طلب متزامن |
| UI / Responsive Tests | التحقق من الواجهة وتجربة الاستخدام | RTL والهاتف والكمبيوتر وحالات الخطأ |
| PWA Tests | التحقق من التثبيت والسلوك المدعوم | manifest وservice worker والتحديث |
| Printing / Device Tests | التحقق من الوكيل والطابعة | Android USB وEpson TM-T20 |
| Backup / Restore Tests | إثبات قابلية استعادة البيانات | استعادة قاعدة البيانات والملفات |
| Performance / Load / Stress | قياس الاستجابة والسعة والثبات | حمل متدرج وذروة وفترة تشغيل |
| User Acceptance Testing (UAT) | اعتماد المستخدم لتدفقات العمل | العميل والكاشير والإدارة |

## 4. البيئات والبيانات المستخدمة

### 4.1 البيئات

| البيئة | الاختبارات المسموح بها |
|---|---|
| Development | Unit وFeature وتجارب المطور |
| CI / Test | اختبارات آلية مع بيانات اصطناعية وخدمات اختبار |
| Staging | تكامل شامل وE2E وUAT واختبارات الأجهزة والنسخ والاستعادة |
| Production | فحوص صحة ومراقبة واختبارات محدودة مصرح بها لا تؤثر على العملاء أو الماليات |

- يمنع تشغيل اختبارات ضغط أو اختبارات إتلاف بيانات على الإنتاج.
- يجب منع Staging من الوصول إلى طابعة الإنتاج أو بوابات دفع حقيقية غير مصرح بها.
- لكل بيئة قاعدة بيانات وإعدادات وأسرار منفصلة.
- لا يوجد أي اتصال ببيانات أو خدمات المشروع القديم.

### 4.2 بيانات الاختبار

تُنشأ بيانات اصطناعية تمثل الحالات المطلوبة، مثل:

- عميل ضيف وعميل مسجل.
- مدير بصلاحيات كاملة ومدير بصلاحيات محدودة.
- كاشير بصلاحيات مختلفة.
- مناطق توصيل برسوم وحدود دنيا مختلفة.
- منتجات متاحة وغير متاحة ومنتجات بخيارات وإضافات.
- طلب استلام وطلب توصيل.
- طلبات بحالات تشغيلية مختلفة.
- حالات دفع ناجحة ومرفوضة ومعلقة وفق وسائل الدفع التي ستعتمد.
- مهام طباعة ناجحة وفاشلة ومنتظرة وإعادة طباعة.
- مستخدمون معطلون وجلسات منتهية.
- بيانات ملفات وصور سليمة وأخرى مخالفة لقيود الرفع.

يجب أن تكون قيم الأسعار والرسوم في بيانات الاختبار معروفة مسبقًا، وتستخدم لاختبار الحسابات دون اعتماد قيم تشغيلية فعلية للمطعم.

## 5. قواعد التوثيق والتتبع

كل حالة اختبار يجب أن تحتوي على:

| الحقل | الوصف |
|---|---|
| Test Case ID | معرف فريد مثل TC-ORD-001 |
| Requirement ID | المتطلب أو معيار القبول المرتبط |
| Title | اسم الاختبار |
| Preconditions | الشروط المسبقة |
| Test Data | بيانات الاختبار |
| Steps | خطوات التنفيذ |
| Expected Result | النتيجة المتوقعة |
| Actual Result | النتيجة الفعلية |
| Status | Not Run / Pass / Fail / Blocked |
| Environment | البيئة والإصدار |
| Evidence | رابط سجل أو صورة أو تقرير مناسب |
| Defect ID | رقم العيب عند الفشل |

لا تستخدم حالة Pass دون تنفيذ فعلي. وتظل الحالة Not Run إلى أن يتم تشغيلها.

## 8. اختبارات الكاشير والإدارة

### 8.1 الكاشير

- تسجيل الدخول والخروج وانتهاء الجلسة.
- عرض الطلبات حسب الحالة والنوع والفترة.
- تحديث قائمة الطلبات دون فقد مدخلات المستخدم أو موضعه.
- فتح تفاصيل الطلب ومطابقة الأصناف والخيارات والعنوان والإجمالي.
- إنشاء طلب يدوي بنفس قواعد التسعير والتحقق الخاصة بالعميل.
- تعديل الطلب وفق حالته والصلاحية مع حفظ سجل التعديل.
- إدارة الوردية وحركات الصندوق وفق القواعد التي ستعتمد.
- إظهار حالة الطلب والدفع والطباعة كلٌ على حدة.
- ظهور وسيلة «رابط دفع» في الفاتورة عندما تكون مختارة.
- عدم وجود وظيفة داخل نظام فتوش لإنشاء رابط الدفع أو إرساله أو الاتصال بلوحة مزود الدفع.
- فتح الكاشير لوحة البنك الخارجية وإنشاء الرابط وإرساله للعميل منها.
- عدم تعديل الكاشير لأي بيانات أو حالة دفع داخل نظام فتوش بعد الإرسال.
- رفض إجراء غير مصرح به حتى عند استدعاء المسار مباشرة.
- عدم كشف بيانات العميل غير اللازمة لدور الكاشير أو المطبخ.

### 8.2 الإدارة

- إنشاء وتعديل وإخفاء الأقسام والمنتجات.
- إدارة الصور والتحقق من النوع والحجم والامتداد.
- إدارة الخيارات الإلزامية والاختيارية وقواعد التسعير.
- إدارة مناطق التوصيل ورسومها والحد الأدنى.
- التحقق من تسجيل تغييرات الأسعار والرسوم والصلاحيات في سجل التدقيق.
- إدارة المستخدمين والأدوار والصلاحيات.
- مراجعة الطلبات والتقارير وفق صلاحية الدور.
- حماية الإعدادات الحساسة والنسخ والاستعادة.
- إظهار الأخطاء والسجلات دون كشف أسرار أو بيانات حساسة.

### 8.3 مصفوفة صلاحيات

ينشأ جدول اختبار يضم على الأقل:

| الدور التجريبي | مشاهدة الطلبات | تعديل الأسعار | إدارة المستخدمين | إعادة الطباعة | استعادة نسخة |
|---|---|---|---|---|---|
| عميل | طلباته المسموح بها فقط | لا | لا | لا | لا |
| كاشير | وفق نطاقه | لا افتراضيًا | لا افتراضيًا | فقط إذا منحت الصلاحية | لا |
| مدير محدود | وفق الدور | حسب المنح | حسب المنح | حسب المنح | لا افتراضيًا |
| مدير مخول | وفق الصلاحيات المعتمدة | عند السماح | عند السماح | عند السماح | لصلاحية شديدة التقييد |

هذه مصفوفة اختبار مبدئية وليست اعتمادًا نهائيًا لتوزيع صلاحيات الأدوار. يجب اعتماد قائمة الصلاحيات الفعلية قبل اختبار قبولها.

## 9. اختبارات Module Manager والاعتماديات

- تفعيل وحدة مستقلة لا تتسبب في كسر وحدات أخرى.
- رفض تعطيل وحدة تعتمد عليها وحدة فعالة دون معالجة الاعتمادية.
- رفض تفعيل وحدة عند غياب اعتماد إلزامي.
- منع تعطيل وحدة حرجة يحتاجها النظام الأساسي.
- تسجيل من فعّل أو عطّل الوحدة ووقت العملية ونتيجتها.
- عدم حذف مجلدات أو ملفات الوحدات يدويًا.
- عدم تنفيذ migration مدمرة تلقائيًا لمجرد تعطيل وحدة.
- اختبار سلامة النظام بعد التفعيل أو التعطيل.
- التحقق من أن الواجهة والـ API والخدمات الخلفية تحترم حالة الوحدة.

تُبنى هذه الاختبارات بعد اعتماد مخطط الاعتماديات وسلوك التفعيل/التعطيل.

## 11. اختبارات الأمان والخصوصية

تجرى اختبارات أمان على الأقل للفئات التالية:

- المصادقة: كلمات المرور والجلسات وتسجيل الخروج واستعادة الحساب.
- التفويض: الوصول المباشر لمسار أو API دون صلاحية.
- عزل الأدوار: منع العميل والكاشير من عمليات الإدارة غير المصرح بها.
- عزل البيانات: عدم رؤية مستخدم بيانات خارج نطاقه أو فرعه مستقبلًا.
- التحقق من المدخلات: منع إدخال بيانات غير متوقعة أو ضارة.
- حماية CSRF/XSS/SQL Injection وفق إطار التطبيق وأدوات الفحص.
- رفع الملفات: منع الملفات غير المسموح بها والتحقق من الحجم والنوع.
- إدارة الأسرار: التأكد من عدم ظهور مفاتيح أو كلمات مرور في الكود أو السجلات أو رسائل الخطأ.
- Rate Limiting: اختبار الحد من الطلبات المتكررة على المسارات الحساسة بعد اعتماد الحدود.
- Audit: تسجيل العمليات الحساسة وعدم السماح بتعديل السجل من مستخدم عادي.
- HTTPS: التحقق من فرض الاتصال المشفر في الإنتاج.
- الجلسات: إبطال الوصول بعد تعطيل الحساب أو تغيير بيانات الأمان وفق السياسة المعتمدة.
- Print Agent: رفض جهاز غير مسجل أو مهمة غير موثقة، ومنع أوامر غير خاصة بالطباعة.

يجب معالجة نتائج الفحص الأمني قبل الإطلاق وفق مستوى خطورتها. لا تعد هذه الوثيقة بديلًا عن مراجعة أمنية متخصصة إذا تطلب نطاق التكاملات ذلك.

## 12. اختبارات التزامن ومنع التكرار

يجب تصميم بيانات وسيناريوهات لاختبار السباقات والتكرار، ومنها:

1. عميل يضغط تأكيد الطلب عدة مرات بسرعة.
2. إعادة إرسال نفس الطلب بسبب انقطاع الشبكة.
3. طلبان متزامنان على آخر كمية متاحة من منتج إذا تم اعتماد إدارة المخزون.
4. كاشيران يعدلان حالة الطلب نفسها في الوقت ذاته.
5. تعديل رسوم منطقة أثناء محاولة تأكيد طلب.
6. تكرار callback أو نتيجة دفع.
7. تكرار استلام Print Job من الوكيل.
8. إعادة محاولة Queue بعد انتهاء مهلة التنفيذ.
9. تشغيل أكثر من Worker على مهام متقاربة.
10. تنفيذ migration أو مهمة مجدولة بالتوازي دون السماح بتضاربها.

النتائج المطلوبة:

- عدم إنشاء طلبات مكررة لنفس عملية التأكيد.
- عدم تسجيل دفع مرتين.
- عدم احتساب رسوم أو خصم أكثر من مرة.
- عدم تطبيق انتقال حالة متعارض بصمت.
- عدم فقد مهمة طباعة محفوظة.
- وجود نتيجة واضحة عند التعارض وإمكانية المراجعة.
- استخدام معاملات وقفل/آليات منع التكرار وفق تصميم قاعدة البيانات والمعمارية المعتمد.

تحدد أحجام الحمل المتزامن بعد اعتماد أهداف الأداء وبيئة الاختبار؛ لا تضع هذه الوثيقة رقمًا مستهدفًا من تلقاء نفسها.

## 13. اختبارات واجهة المستخدم وPWA

### 13.1 الواجهة

- RTL فعلي في الصفحات والنماذج والجداول والرسائل.
- اختبار الهاتف والكمبيوتر والجهاز اللوحي.
- وضوح النصوص والحقول والأزرار وحالات التركيز.
- قابلية الاستخدام باللمس ولوحة المفاتيح.
- عدم الاعتماد على اللون وحده لتمييز الحالة.
- اختبار Loading وEmpty وError وOffline وPermission Denied وConflict.
- عدم إظهار رسالة نجاح قبل تأكيد الخادم.
- عدم فقد المدخلات عند خطأ قابل للتصحيح.
- عدم عرض أزرار أو إجراءات لا تسمح بها الصلاحية.
- اختبار الصور وأسماء الأصناف ومطابقتها للمنتجات.

### 13.2 PWA

- التحقق من Web App Manifest وبيانات الاسم والأيقونات.
- التحقق من Service Worker وسلوك التحديث.
- التحقق من إمكانية التثبيت على الأجهزة والمتصفحات المدعومة.
- اختبار فتح التطبيق بعد التثبيت.
- اختبار سلوك فقد الاتصال وعودته.
- التأكد من عدم تأكيد طلب أو دفع اعتمادًا على بيانات Offline قديمة دون تحقق خادمي.
- اختبار تحديث النسخة وعدم بقاء ملفات واجهة قديمة بصورة تكسر التوافق.
- توثيق اختلافات التثبيت والسلوك بين iOS وAndroid والمتصفحات المستهدفة.

لا يفترض أن جميع وظائف الطلب أو الدفع تعمل Offline؛ يحدد ذلك صراحة في تصميم PWA قبل التنفيذ.

## 14. اختبارات النسخ الاحتياطي والاستعادة والتشغيل

- التحقق من تنفيذ النسخ حسب الجدول الذي سيعتمد.
- التحقق من تشفير النسخة وصلاحيات الوصول.
- التحقق من تسجيل نتيجة النسخ والتنبيه عند الفشل.
- استعادة قاعدة البيانات في بيئة معزولة.
- استعادة ملفات وصور المنتجات.
- فحص العلاقات والبيانات الأساسية بعد الاستعادة.
- تسجيل الزمن الفعلي للاستعادة.
- اختبار Health Checks بعد الاستعادة.
- اختبار تراجع إصدار التطبيق على Staging.
- اختبار فشل Redis أو Worker والتحقق من عدم فقد طلب محفوظ.
- اختبار تراكم Queue ثم عودة المعالجة.
- اختبار انقطاع Print Agent ثم عودته.

تظل قيم RPO وRTO وتكرار النسخ ومدد الاحتفاظ قرارات مفتوحة في وثيقة DevOps، ويجب اعتمادها وقياسها.

- استهلاك CPU والذاكرة والتخزين.
- زمن استجابة Print Job API والوكيل.

### 15.2 أنواع القياس

- Baseline: قياس الأداء قبل اختبارات الحمل.
- Load: حمل تدريجي يمثل الاستخدام المتوقع بعد اعتماده.
- Stress: زيادة الحمل حتى ظهور حدود أو تدهور الخدمة في بيئة اختبار.
- Spike: زيادة مفاجئة في الحمل.
- Soak: تشغيل ممتد لرصد تسرب الموارد أو تدهور الأداء.
- Recovery: قياس التعافي بعد انتهاء الحمل أو توقف مكون.

### 15.3 التقرير المطلوب

يحتوي تقرير الأداء على:

- مواصفات بيئة الاختبار.
- إصدار التطبيق والالتزام البرمجي.
- حجم بيانات الاختبار.
- سيناريوهات الحمل وعدد المستخدمين الافتراضيين.
- زمن الاستجابة ومقاييس التوزيع المناسبة.
- معدل الأخطاء.
- استهلاك الموارد.
- اختناقات قاعدة البيانات أو Redis أو Queue.
- حدود الاختبار والملاحظات.
- توصيات التحسين وإعادة الاختبار.

لا تعتمد أرقام زمن استجابة أو عدد مستخدمين أو طلبات في الثانية قبل تحديد أهدافها وقياسها على البنية الفعلية.

## 16. اختبار قبول المستخدم UAT

يُنفذ مع ممثلين عن أدوار النظام الثلاثة:

### العميل

- تصفح الأقسام والمنتجات والصور.
- اختيار الخيارات وإضافة الأصناف للسلة.
- إنشاء طلب استلام دون عنوان أو حد أدنى أو رسوم توصيل.
- إنشاء طلب توصيل مع المنطقة والعنوان والحد الأدنى والرسوم.
- مراجعة الطلب وتأكيده ومتابعة حالته.

### الكاشير

- تسجيل الدخول وفتح شاشة الطلبات.
- استقبال طلب جديد ومراجعة تفاصيله.
- تحديث الحالة وفق الصلاحيات.
- إنشاء طلب يدوي.
- متابعة الدفع والوردية وفق النطاق المعتمد.
- معرفة حالة الطباعة والتعامل مع الفشل.
- إعادة الطباعة وفق الصلاحية والإجراء المعتمد.

### المدير

- إدارة المنتجات والأقسام والصور.
- إدارة مناطق التوصيل ورسومها وحدودها.
- إدارة المستخدمين والصلاحيات.
- مراجعة السجلات والتقارير.
- مراجعة حالة النظام والنسخ الاحتياطي والطباعة وفق الصلاحيات.

يسجل لكل سيناريو: المنفذ، التاريخ، الإصدار، النتيجة، الملاحظات، العيوب، قرار القبول. ولا يعتبر UAT مكتملًا بمجرد استعراض الشاشات؛ يجب تنفيذ مهام فعلية ببيانات اختبار.

## 17. إدارة العيوب (Defect Management)

### 17.1 درجات الخطورة المقترحة

| المستوى | الوصف | أمثلة |
|---|---|---|
| Critical | خطر أمني أو مالي جسيم أو فقد بيانات أو توقف المسار الأساسي | كشف بيانات حساسة، طلبات/مدفوعات مكررة، فقد الطلبات |
| High | تعطل وظيفة أساسية دون بديل مقبول | عدم إمكانية إتمام طلبات التوصيل أو فشل تسجيل الدخول للكاشير |
| Medium | خلل مؤثر مع وجود بديل مؤقت | خطأ في فلتر أو شاشة غير أساسية |
| Low | خلل بصري أو نصي محدود | محاذاة أو تسمية غير مؤثرة |

### 17.2 دورة العيب

`New → Triaged → Assigned → In Progress → Fixed → Retest → Closed`

إذا فشل إعادة الاختبار يعاد فتح العيب. يجب أن يحتوي تقرير العيب على خطوات إعادة الإنتاج والنتيجة المتوقعة والفعلية والبيئة والإصدار والدليل.

لا تغلق عيوبًا حرجة أو عالية لمجرد وجود حل يدوي مؤقت دون موافقة صريحة وتقييم للمخاطر.

## 18. بوابات الجودة قبل الدمج والإطلاق

### بوابة Pull Request

- مراجعة الكود.
- نجاح الفحوص الآلية الإلزامية.
- نجاح Unit وFeature Tests ذات الصلة.
- عدم وجود أسرار أو بيانات حقيقية في التغيير.
- مراجعة migrations والعقود والصلاحيات عند تأثرها.

### بوابة Staging

- نجاح اختبارات التكامل.
- نجاح تدفقات E2E الحرجة.
- نجاح اختبارات الصلاحيات.
- نجاح اختبار واجهات الأجهزة المستهدفة.
- مراجعة السجلات والأخطاء.
- اختبار النشر والتراجع عند انطباقه.

### بوابة Production Release

- اكتمال UAT واعتماده.
- لا توجد عيوب Critical أو High مفتوحة، إلا استثناء مكتوب وموافق عليه من صاحب القرار مع خطة معالجة ومخاطر موثقة.
- نجاح اختبارات الطلب والتسعير والدفع والطباعة الحرجة.
- وجود نسخة احتياطية قابلة للتحقق وخطة استعادة.
- وجود خطة نشر وتراجع معتمدة.
- جاهزية المراقبة والتنبيهات.
- اعتماد المستخدم المسؤول للإطلاق.

## 20. التقارير ومؤشرات جودة الإصدار

يصدر تقرير لكل نسخة مرشحة يحتوي على:

- عدد الاختبارات المخططة والمنفذة والمتجاوزة والمحظورة.
- عدد حالات Pass وFail وBlocked وNot Run.
- العيوب المفتوحة حسب الخطورة.
- نتائج الاختبارات الحرجة.
- نتائج الأمن والصلاحيات.
- نتائج التزامن ومنع التكرار.
- نتائج الطباعة والأجهزة.
- نتائج النسخ والاستعادة.
- نتائج الأداء مع مواصفات بيئة القياس.
- قرار Go / No-Go وأسباب القرار.
- موافقات UAT والنشر.

لا تستخدم نسبة نجاح عامة لإخفاء فشل اختبار حرج؛ يجب إبراز الاختبارات الحرجة بصورة مستقلة.

## 22. خطة تنفيذ الاختبارات حسب مراحل التطوير

1. مع كل وحدة: Unit وFeature Tests قبل دمجها.
2. عند ربط وحدتين: Integration وContract Tests.
3. عند اكتمال تدفق العميل: E2E للاستلام والتوصيل.
4. عند اكتمال الكاشير: E2E للطلبات والوردية والطباعة.
5. عند اكتمال الإدارة: اختبارات إدارة المنتجات والمناطق والمستخدمين والصلاحيات.
6. قبل إصدار Staging: Regression Tests للتدفقات التي سبق اعتمادها.
7. في Staging: اختبارات الأجهزة والطباعة وPWA وUAT.
8. قبل الإنتاج: Security وLoad/Stress وBackup/Restore وRelease Gate.
9. بعد النشر: Health Checks ومراقبة الإصدار وفق DevOps Plan.

لا تنتظر نهاية المشروع لتبدأ الاختبارات؛ تنفذ بالتوازي مع تسليم الوحدات، مع بقاء اختبارات القبول الشاملة قبل الإطلاق.
