## 1. الهدف والنطاق

تحدد هذه الوثيقة طريقة تجهيز وإدارة بيئات النظام الجديد، وتنظيم العمل على GitHub، وفحص التغييرات قبل دمجها، ونشر الإصدارات، ومراقبة الخدمة، وحماية البيانات، والنسخ الاحتياطي والاستعادة.

الأهداف:

1. فصل التطوير والاختبار عن الإنتاج منعًا لتأثر المطعم بتجارب التطوير.
2. منع وصول أي بيئة إلى قاعدة بيانات بيئة أخرى.
3. ضمان عدم نشر كود غير مفحوص إلى الإنتاج.
4. حفظ أسرار التشغيل خارج GitHub والكود.
5. توفير طريقة نشر وتراجع موثقة وقابلة للتكرار.
6. مراقبة التطبيق وقاعدة البيانات وRedis والصفوف الخلفية والطباعة.
7. إثبات إمكانية استعادة البيانات باختبار فعلي.
8. ضبط تكلفة البنية التحتية بعد تحديد الميزانية ومتطلبات التشغيل، لا بافتراض مزود أو سعر.

خارج نطاق هذه الوثيقة: شراء الاستضافة أو النطاق، إنشاء الخدمات الفعلية، إنشاء حسابات مزودي الخدمات، كتابة ملفات Workflow أو إعداد الخادم. هذه أعمال تنفيذية لاحقة تتطلب اعتمادًا منفصلًا.

## 2. البيئات المعتمدة مبدئيًا

يقترح اعتماد ثلاث بيئات منفصلة منطقيًا وتقنيًا:

| البيئة | الاستخدام | البيانات | الوصول |
|---|---|---|---|
| Development | التطوير اليومي وتجارب المطورين | بيانات تجريبية فقط | المطورون المصرح لهم |
| Staging / Testing | اختبار الإصدار قبل الإنتاج واختبار قبول المستخدم | بيانات اختبار غير حقيقية أو منزوعة الهوية | فريق الاختبار والمستخدم المعتمد |
| Production | تشغيل مطعم فتوش الخالدية فعليًا | بيانات التشغيل الحقيقية | المستخدمون المصرح لهم فقط |

### 2.1 متطلبات الفصل

- لكل بيئة إعدادات مستقلة وملف أسرار مستقل وقاعدة بيانات مستقلة.
- Redis مستقل لكل بيئة أو نطاق عزل موثق يمنع مشاركة المفاتيح والصفوف بين البيئات.
- لا تستخدم بيئة التطوير أو الاختبار قاعدة بيانات الإنتاج.
- لا تنسخ بيانات العملاء أو الطلبات الحقيقية إلى التطوير أو الاختبار دون سياسة معتمدة لإخفاء الهوية وموافقة مناسبة.
- لا تستخدم بيانات اعتماد المشروع القديم أو اتصالاته أو خدماته.
- لا يُسمح لتطبيق الاختبار بتنفيذ عمليات على طابعة الإنتاج.
- يجب أن تكون أسماء الخدمات وقواعد البيانات والـ queues والـ storage واضحة وتحمل اسم البيئة.
- يمنع تشغيل أوامر الصيانة أو migrations على الإنتاج من جهاز المطور مباشرة دون مسار نشر مصرح ومسجل.

### 2.2 عناوين البيئات

لم يتم اختيار النطاق بعد. يمكن لاحقًا اعتماد نطاقات فرعية مثل:

- `dev.<domain>`
- `staging.<domain>`
- النطاق الرسمي للإنتاج

هذه أمثلة تنظيمية فقط وليست أسماء نطاقات محجوزة أو مؤكدة. يجب ألا تُفتح واجهات الإدارة أو الاختبار للعامة دون حماية مناسبة.

## 3. تنظيم GitHub والفروع

المستودع المعتمد للمشروع الجديد:

`Malek-9292/kheralden92`

### 3.1 نموذج الفروع المقترح

| الفرع | الغرض | سياسة الدمج |
|---|---|---|
| `main` | النسخ المعتمدة المرشحة للإنتاج والإصدارات المنشورة | Pull Request ومراجعة وفحوص ناجحة |
| `development` | تجميع التطوير واختبار التكامل | Pull Request وفحوص ناجحة |
| `feature/<name>` | ميزة أو وحدة محددة | يبدأ من development ويعود إليه |
| `fix/<name>` | إصلاح محدد | يبدأ من الفرع المناسب ويعود إليه |
| `hotfix/<name>` | إصلاح عاجل للإنتاج | مراجعة واختبارات ثم دمج منظم إلى main وdevelopment |

هذا النموذج مقترح ويحتاج اعتمادًا. لا يُنشأ أي فرع أو تغيير حماية تلقائيًا ضمن هذه الوثيقة.

### 3.2 قواعد المستودع

- تفعيل حماية `main` ويفضل `development` بعد اعتماد الفريق.
- منع Push المباشر إلى `main` بعد تفعيل الحماية.
- اشتراط Pull Request قبل الدمج.
- اشتراط نجاح الفحوص الآلية المحددة.
- طلب مراجعة واحدة على الأقل من شخص مخول، إذا كان حجم الفريق يسمح بذلك.
- منع Force Push وحذف الفروع المحمية إلا بإجراء إداري استثنائي موثق.
- ربط كل Pull Request بوصف واضح للمشكلة والتغيير وطريقة الاختبار.
- استخدام Git Tags للإصدارات المنشورة، مثل `v1.0.0` بعد اعتماد سياسة الترقيم.
- عدم وضع كلمات مرور أو مفاتيح API أو ملفات `.env` أو نسخ قواعد بيانات في المستودع.
- الاحتفاظ بملف `.env.example` يحتوي أسماء المتغيرات وقيمًا توضيحية غير سرية فقط.

### 3.3 سياسة المراجعة

يجب أن يوضح كل طلب دمج:

1. ما الذي تغير ولماذا؟
2. الوحدات أو العقود المتأثرة.
3. هل توجد migrations أو تغييرات بيانات؟
4. ما الاختبارات التي نُفذت؟
5. هل توجد آثار على الصلاحيات أو الخصوصية أو الأداء؟
6. هل توجد خطوات تشغيل أو تراجع مطلوبة؟

لا يُقبل دمج تغيير يكسر حدود الوحدات أو يتجاوز قواعد العمل المعتمدة دون مراجعة وتحديث الوثائق ذات الصلة.

## 4. خط CI/CD المقترح

الهدف من خط CI/CD هو فحص التغيير وإعداده للنشر بصورة متكررة. أداة التنفيذ لم تُحسم بعد، ويمكن تقييم GitHub Actions أو بديل مناسب عند اعتماد الاستضافة.

### 4.1 فحوص كل Pull Request

يقترح أن يشمل خط الفحص:

1. التحقق من إصدار PHP والحزم المطلوبة وفق إصدارات المشروع المعتمدة.
2. تثبيت الاعتماديات من ملفات القفل المعتمدة دون تحديث عشوائي للحزم.
3. فحص تنسيق الكود ومعايير الجودة.
4. فحص التحليل الساكن عند اعتماد أدواته.
5. فحص الاعتماديات بحثًا عن ثغرات معروفة.
6. تشغيل اختبارات Unit وFeature.
7. تشغيل اختبارات التكامل على خدمات اختبار منفصلة.
8. فحص migrations على قاعدة بيانات اختبار مؤقتة أو مخصصة.
9. بناء وتجهيز ملفات الواجهة عند وجود خطوة بناء.
10. حفظ نتائج الفحوص وربطها بطلب الدمج.

لا يُدمج التغيير إذا فشل فحص إلزامي، إلا باستثناء موثق ومصرح.

### 4.2 مسار النشر

المسار المقترح:

`Feature Branch → Pull Request → CI Checks → development → Staging → User Acceptance → main / Release Tag → Production Approval → Deploy → Health Checks`

- نشر `development` إلى بيئة التطوير أو التكامل بعد نجاح الفحوص.
- نشر نسخة مرشحة إلى Staging.
- تنفيذ اختبارات القبول والتأكد من الوظائف الحرجة.
- اعتماد إصدار واضح قبل نشر الإنتاج.
- يتطلب نشر الإنتاج موافقة شخص مخول.
- بعد النشر تنفذ فحوص صحة التطبيق والاتصال بقاعدة البيانات وRedis والصفوف.
- عند فشل فحوص ما بعد النشر، يتم تفعيل إجراء التراجع أو الاستعادة المحدد مسبقًا.

### 4.3 قاعدة البيانات وعمليات Migrations

- تحفظ migrations في Git وتراجع مثل أي كود آخر.
- تجرب migrations على Staging قبل الإنتاج.
- تؤخذ نسخة احتياطية مناسبة قبل تغييرات الإنتاج ذات المخاطر.
- يجب أن تكون تغييرات الجداول متوافقة قدر الإمكان مع الإصدار السابق أثناء النشر التدريجي.
- يفضل نمط Expand / Migrate / Contract للتغييرات التي لا يمكن نشرها دفعة واحدة دون توقف.
- لا ينفذ rollback تلقائيًا إذا كان قد يؤدي إلى فقد بيانات.
- التراجع عن كود التطبيق لا يعني التراجع الآلي عن تغييرات قاعدة البيانات.
- أي migration مدمرة أو حذف بيانات يتطلب خطة مستقلة وموافقة ونسخة احتياطية قابلة للاستعادة.
- لا تنفذ أوامر migrations من أكثر من نسخة تطبيق بالتوازي دون قفل أو آلية تمنع التعارض.

## 5. إعدادات التطبيق والأسرار

### 5.1 إعدادات كل بيئة

يجب أن تكون إعدادات كل بيئة مستقلة وتشمل، حسب الحاجة:

- وضع تشغيل Laravel ومستوى إظهار الأخطاء.
- عنوان التطبيق والنطاقات المسموح بها.
- بيانات اتصال MySQL.
- بيانات اتصال Redis.
- إعدادات Queue وScheduler.
- إعدادات البريد أو الرسائل عند اعتماد مزود.
- إعدادات التخزين ورفع الصور.
- إعدادات الجلسات والتخزين المؤقت.
- إعدادات الطباعة وتسجيل Print Agent.
- إعدادات المراقبة والتنبيه.
- مفاتيح التشفير والتكاملات.

### 5.2 إدارة الأسرار

- لا تحفظ أسرارًا حقيقية داخل GitHub أو ملفات الكود أو الوثائق.
- تستخدم آلية أسرار آمنة لدى مزود الاستضافة أو مدير أسرار مناسب.
- لكل بيئة مفاتيحها وبيانات اعتمادها الخاصة.
- تقتصر صلاحية قراءة الأسرار على من يحتاجها فعليًا.
- تدوّر المفاتيح عند الاشتباه بتسربها أو عند تغيير المسؤولين وفق سياسة معتمدة.
- لا تظهر الأسرار في Logs أو رسائل الخطأ أو تقارير CI.
- لا تشارك كلمات المرور أو مفاتيح الإنتاج عبر محادثات أو ملفات عامة.
- يجب تقييد صلاحيات حساب قاعدة البيانات بأقل الصلاحيات اللازمة، وعدم استخدام حساب root للتطبيق.

### 5.3 ملفات وأدوات ممنوعة من المستودع

على الأقل:

- `.env` وملفات الأسرار الفعلية.
- مفاتيح SSH الخاصة وشهادات التوقيع الخاصة.
- كلمات مرور قواعد البيانات ومفاتيح Redis.
- رموز الوصول الشخصية وAPI Tokens.
- نسخ قواعد البيانات والنسخ الاحتياطية.
- سجلات تحتوي بيانات عملاء أو معلومات حساسة.
- ملفات تخزين جلسات أو بيانات تشغيل مؤقتة.

## 6. بنية تشغيل التطبيق

التقنيات المرجعية في وثيقة المعمارية هي PHP / Laravel / MySQL 8 / Livewire / Alpine.js / Redis / PWA. لا تزال إصدارات الحزم والاستضافة النهائية غير معتمدة.

### 6.1 مكونات التشغيل

| المكوّن | المسؤولية التشغيلية |
|---|---|
| Web Application | استقبال طلبات الويب وتشغيل واجهات Laravel |
| MySQL 8 | تخزين الطلبات والمنتجات والعملاء والبيانات التشغيلية |
| Redis | Cache وQueue وفق الاستخدام المعتمد |
| Queue Workers | تنفيذ الأعمال الخلفية وإعادة المحاولة وفق السياسة |
| Scheduler | تشغيل المهام المجدولة المعتمدة |
| File Storage | تخزين صور المنتجات والملفات المسموح بها |
| HTTPS / TLS | تشفير الاتصال الخارجي |
| Monitoring | مراقبة التطبيق والخدمات والموارد |
| Print Agent | استقبال مهام الطباعة المصرح بها وإرسالها إلى الطابعة المحلية |

### 6.2 تشغيل Laravel

يجب أن تتضمن بيئة الإنتاج إعدادًا آمنًا ومناسبًا لـ Laravel، ومنه:

- تعطيل وضع Debug في الإنتاج.
- استخدام إعدادات تشغيل محسنة بعد اعتماد طريقة النشر.
- توجيه الطلبات إلى مجلد الويب العام الصحيح فقط.
- منع الوصول المباشر إلى ملفات البيئة والكود والسجلات.
- ضبط صلاحيات الملفات والمجلدات بأقل ما يلزم.
- إعداد جلسات آمنة وCookies مناسبة وHTTPS.
- تشغيل Queue Workers كخدمات مستمرة يديرها مشرف عمليات مناسب.
- إعادة تشغيل العمال بطريقة منظمة عند نشر إصدار جديد.
- تشغيل Scheduler بطريقة واحدة موثوقة لكل بيئة لتجنب تكرار المهام.
- ضبط Timezone موحد ومفهوم؛ المنطقة التشغيلية للمطعم هي الكويت، ويجب توثيق سياسة التخزين والعرض الزمني قبل التنفيذ.

### 6.3 Redis والصفوف الخلفية

- Redis ليس بديلًا عن قاعدة البيانات الدائمة للطلبات والمدفوعات.
- لا يعتمد حفظ الطلب الأساسي على نجاح مهمة Queue لاحقة.
- تستخدم الصفوف للمهام غير الفورية أو القابلة لإعادة المحاولة.
- تراقب المهام المتراكمة والفاشلة ومدة تنفيذها.
- تحدد سياسات retry وbackoff وdead-letter أو آلية مراجعة مكافئة.
- يجب منع تكرار الآثار الجانبية عند إعادة المحاولة باستخدام مفاتيح idempotency أو آلية مناسبة.
- تحدد سياسة استمرار المهام عند إعادة تشغيل Redis أو Worker واختبارها.
- يجب عزل أسماء queues وRedis keys بين البيئات.

### 6.4 التخزين والملفات

- تخزن صور المنتجات والملفات في مساحة تخزين مناسبة وليست داخل مجلد مؤقت قابل للمسح عند النشر.
- يحدد مزود التخزين وسياسة الاحتفاظ والنسخ الاحتياطي بعد اختيار الاستضافة.
- يجب التحقق من نوع وحجم الملفات المرفوعة، وإعادة تسمية الملفات وفق سياسة آمنة.
- لا يسمح بتنفيذ ملفات مرفوعة أو تقديمها كملفات برمجية.
- يجب أن تتوفر خطة لاستعادة الصور والملفات المهمة بالتوازي مع قاعدة البيانات.
- يجب اختبار روابط الصور والصلاحيات بعد النشر.

## 7. النطاق وDNS وHTTPS

لم يتم شراء أو اختيار نطاق بعد.

قبل الإطلاق يجب:

1. اختيار اسم النطاق وشراؤه من جهة موثوقة بعد اعتماد الميزانية.
2. ضبط DNS وفق تعليمات مزود الاستضافة.
3. تفعيل HTTPS بشهادة صالحة وتجديد آلي أو إجراء تجديد موثق.
4. فرض تحويل HTTP إلى HTTPS.
5. حماية لوحة الإدارة ومسارات التشغيل الحساسة.
6. ضبط النطاقات المسموح بها وCORS وCSRF وفق بنية التطبيق.
7. اختبار انتهاء الشهادة وتجديدها والتنبيه قبل الانتهاء.
8. تحديد سياسة البريد الإلكتروني وDNS records إذا تم اعتماد البريد.

لا يتم وضع اسم نطاق أو مزود أو سعر في الخطة قبل قرار المستخدم والتحقق من الخيارات وقت الشراء.

## 8. استراتيجية النشر والتراجع

### 8.1 النشر

يجب أن يكون النشر:

- مبنيًا على إصدار أو commit معروف.
- قابلًا للتكرار والتتبع.
- منفصلًا عن عمليات التطوير اليومية.
- مصحوبًا بنتائج CI وسجل نشر.
- متبوعًا بفحوص صحة.
- معتمدًا قبل التأثير على الإنتاج.

تتضمن قائمة النشر المناسبة حسب التغيير:

1. مراجعة الإصدار وPull Requests.
2. التحقق من نجاح الاختبارات.
3. التأكد من جاهزية قاعدة البيانات والنسخة الاحتياطية عند الحاجة.
4. تنفيذ خطوات الصيانة المعتمدة.
5. نشر إصدار التطبيق.
6. تشغيل migrations المراجعة عند الحاجة.
7. إعادة تشغيل workers والخدمات المتأثرة.
8. فحص الصفحة الرئيسية وتسجيل الدخول والاتصال بقاعدة البيانات وRedis.
9. فحص إنشاء طلب تجريبي آمن في بيئة الاختبار، لا في بيانات الإنتاج إلا وفق إجراء معتمد.
10. مراجعة السجلات ومؤشرات الأخطاء بعد النشر.

### 8.2 التراجع Rollback

- يجب الاحتفاظ بالإصدار السابق القابل للنشر.
- يحدد لكل إصدار ما إذا كان التراجع عن التطبيق آمنًا مع مخطط قاعدة البيانات الحالي.
- لا تنفذ استعادة قاعدة البيانات لمجرد فشل إصدار جديد دون تقييم أثر البيانات التي دخلت بعد النشر.
- عند الحاجة لاستعادة بيانات، ينفذ الإجراء بواسطة مسؤول مخول مع تسجيل السبب والوقت والنتيجة.
- يجب اختبار إجراء التراجع في Staging قبل اعتماده للإنتاج.
- توثق نقطة القرار التي تستدعي التراجع، مثل فشل فحوص الصحة أو ارتفاع أخطاء حرجة.

## 9. النسخ الاحتياطي والاستعادة

### 9.1 نطاق النسخ

يجب تحديد سياسة تشمل:

- قاعدة بيانات MySQL.
- صور المنتجات والملفات الدائمة.
- إعدادات التشغيل غير السرية التي يلزم توثيقها.
- سجلات التدقيق أو البيانات التشغيلية التي يتطلب الاحتفاظ بها.
- ملفات إعدادات البنية التحتية التي يمكن إعادة إنشائها بأمان، دون تضمين أسرار مكشوفة.

### 9.2 ضوابط النسخ

- تشفير النسخ الاحتياطية أثناء النقل والتخزين.
- فصل صلاحيات النسخ عن صلاحيات الاستعادة قدر الإمكان.
- حفظ نسخة خارج بيئة الخادم الأساسية إذا سمحت الميزانية والبنية.
- تحديد مدة الاحتفاظ وتكرار النسخ بعد اعتماد RPO/RTO والتكلفة.
- مراقبة نجاح وفشل كل عملية نسخ.
- تسجيل وقت النسخ ونوعه ومكانه وحالته دون كشف بيانات حساسة.
- تقييد الوصول إلى النسخ الاحتياطية.
- عدم اعتبار النسخة ناجحة لمجرد اكتمال أمر النسخ؛ يجب التحقق من سلامتها.

### 9.3 اختبار الاستعادة

- إجراء استعادة تجريبية في بيئة منفصلة.
- التحقق من سلامة الجداول والعلاقات والبيانات الأساسية.
- التحقق من استعادة صور المنتجات والملفات.
- اختبار دخول المستخدمين التجريبيين وإنشاء/قراءة بيانات اختبار.
- قياس الزمن الفعلي للاستعادة وتوثيقه.
- لا تختبر الاستعادة فوق إنتاج حي.
- تسجل نتيجة كل اختبار والإجراءات التصحيحية.

### 9.4 RPO وRTO

لم يتم اعتماد قيم حتى الآن:

- **RPO:** أقصى مقدار بيانات يمكن قبول فقده زمنيًا.
- **RTO:** أقصى مدة مستهدفة لاستعادة الخدمة.

يجب تحديدهما مع المستخدم وفق أثر توقف المطعم وتكلفة البنية والنسخ. لا يجوز اختراع أرقام أو الادعاء بتحقيقها قبل اختبار الاستعادة.

## 10. المراقبة والسجلات والتنبيهات

### 10.1 مؤشرات التطبيق

- توفر الموقع ونسبة أخطاء HTTP.
- زمن الاستجابة للطلبات والواجهات الأساسية.
- أخطاء التطبيق والاستثناءات.
- نجاح وفشل تسجيل الدخول ومحاولات الوصول المرفوضة.
- أخطاء إنشاء الطلب والدفع.
- معدل الطلبات ومؤشرات الحمل عند اعتماد أدوات القياس.

### 10.2 مؤشرات البنية التحتية

- استخدام CPU والذاكرة ومساحة التخزين.
- حالة MySQL والاتصالات والاستعلامات البطيئة.
- حالة Redis واستهلاك الذاكرة.
- عدد المهام المنتظرة والفاشلة في Queue.
- حالة Queue Workers وScheduler.
- نجاح النسخ الاحتياطي ونتائج اختبارات الاستعادة.
- انتهاء شهادات HTTPS.

### 10.3 مؤشرات الطباعة

- آخر اتصال لكل Print Agent.
- حالة الجهاز والطابعة.
- عدد مهام الطباعة المنتظرة والفاشلة.
- زمن استجابة الوكيل.
- نسبة نجاح الطباعة ومحاولات إعادة الإرسال.
- آخر خطأ معروف لكل جهاز.

لا يعني إرسال البيانات إلى الطابعة نجاح خروج الورقة فعليًا؛ يجب تسجيل نتيجة الوكيل وفق ما يستطيع الجهاز إثباته.

### 10.4 سياسة السجلات

تفصل السجلات حسب الغرض:

- Application Logs.
- Security Events.
- Audit Logs.
- Queue / Worker Logs.
- Database / Infrastructure Logs.
- Print Job Logs.

يجب إخفاء كلمات المرور ومفاتيح API وبيانات الدفع الحساسة، وتقليل ظهور بيانات العميل إلى الحد الضروري. تحدد مدد الاحتفاظ والوصول إلى السجلات وفق سياسة الخصوصية والتكلفة.

### 10.5 التنبيهات

تحدد التنبيهات الحرجة بعد اختيار وسيلة الإشعار، وتشمل على الأقل:

- توقف الموقع أو فشل Health Check.
- تعذر الاتصال بقاعدة البيانات.
- توقف Redis أو تراكم Queue بصورة غير طبيعية.
- فشل النسخ الاحتياطي.
- امتلاء مساحة التخزين أو اقترابها من الحد الحرج.
- ارتفاع معدل الأخطاء.
- انقطاع Print Agent أو تراكم مهام الطباعة.
- قرب انتهاء شهادة HTTPS.

يجب أن يكون لكل تنبيه مالك أو إجراء واضح، وألا تتحول التنبيهات إلى رسائل متكررة بلا فائدة.

## 11. فحوص الصحة (Health Checks)

يقترح توفير فحوص منفصلة:

- فحص أساسي يثبت أن التطبيق يستجيب.
- فحص اتصال قاعدة البيانات.
- فحص Redis عند الحاجة.
- فحص Queue Workers وScheduler بمؤشرات مناسبة.
- فحص مساحة التخزين.
- فحص تكامل الطباعة بصورة منفصلة.

يجب ألا تكشف Health Checks العامة أسرارًا أو تفاصيل داخلية. يمكن أن تكون الفحوص التفصيلية محمية ومخصصة للمراقبة الداخلية.

## 12. تشغيل Print Agent والطابعة

الطباعة مكون منفصل عن نشر تطبيق الويب وعن دورة حياة الطلب.

### 12.1 مبدأ التشغيل

- تطبيق Laravel ينشئ مهمة طباعة بعد حفظ الطلب وفق الحدث المعتمد.
- تبقى المهمة محفوظة في النظام حتى لو كان Print Agent غير متصل.
- يتصل Print Agent بالنظام عبر قناة موثقة وآمنة يتم اعتمادها بعد الاختبار.
- لا يقبل الوكيل أوامر تنفيذ عامة أو أوامر نظام من الخادم؛ يقبل أنواع مهام الطباعة المحددة فقط.
- يجب التحقق من هوية الجهاز وصلاحية المهمة ومنع إعادة إرسال المهمة الأصلية دون قصد.
- يسجل الوكيل نتيجة التنفيذ والخطأ التقني الممكن رصده.

### 12.2 الاتصال والأمان

- HTTPS إلزامي للاتصال بين الوكيل والخادم.
- لكل جهاز هوية وبيانات اعتماد قابلة للإلغاء والتدوير.
- لا تعرض واجهة الوكيل على الإنترنت أو الشبكة العامة دون مصادقة وضوابط.
- لا يسمح للوكيل بقراءة ملفات أو تنفيذ أوامر خارج نطاق الطباعة.
- تحدد طريقة الاتصال (Polling أو اتصال صادر آمن أو بديل) بعد اختبار عملي للأجهزة المستهدفة.
- لا يُفترض أن Android USB يعمل على كل الأجهزة لمجرد نجاحه على جهاز واحد.

### 12.3 التوافق والاختبار

- الطابعة المستهدفة: Epson TM-T20.
- الهدف: Android مع اتصال USB.
- يجب إعداد مصفوفة اختبار تشمل موديل جهاز Android وإصدار النظام ونوع وصلة USB والطابعة وعرض الورق.
- يجب اختبار انقطاع الإنترنت، وانقطاع USB، وإعادة تشغيل الجهاز، وتكرار المهمة، وإعادة الطباعة الصريحة.
- لا يعتمد توافق نهائي أو إطلاق إنتاجي قبل نجاح الاختبار على الجهاز الفعلي المستهدف.
- تحديث Print Agent له دورة إصدار واختبار مستقلة عن تطبيق الويب، مع توثيق النسخة المثبتة لكل جهاز.

## 13. الأمان التشغيلي

## 14. السعة والأداء والتكلفة

لا تحدد هذه الوثيقة مواصفات CPU أو RAM أو مساحة أو عدد مستخدمين أو طلبات متزامنة؛ ذلك يتوقف على مزود الاستضافة والميزانية ونتائج القياس.

قبل اختيار الخطة يجب تقدير:

- عدد الطلبات اليومي والمتزامن المتوقع.
- عدد صور المنتجات وحجم الملفات.
- حجم قاعدة البيانات ومعدل نموها.
- عدد عمال Queue.
- احتياج النسخ الاحتياطي والتخزين الخارجي.
- متطلبات المراقبة.
- قرب مركز البيانات من المستخدمين وتأثيره على زمن الاستجابة.
- إمكانات التوسع وقيود المزود.
- التكلفة الشهرية والسنوية والتجديد والضرائب والنسخ الاحتياطية.

بعد إنشاء بيئة مماثلة للإنتاج، تنفذ اختبارات Load وStress وتوثق النتائج قبل تحديد حدود تشغيلية. لا توجد ضمانات سعة دون قياس.
